# work-report — плагин Claude Code для отчётов о выполненной работе — дизайн

Дата: 2026-10-07 · Статус: согласован в чате, ждёт проверки спека

## Зачем

Каждый день сотрудник работает с Claude Code в нескольких репозиториях, а в конце дня
вручную переносит сделанное в таск-трекер; в пятницу вся команда вручную собирает недельный
отчёт по регламенту. Плагин делает это из того, что уже есть на машине: git-истории и
истории сессий Claude Code (плюс claude-mem, если установлен).

Две задачи:

1. **День** — в конце дня выдать карточки выполненных задач для таск-трекера.
2. **Неделя** — в пятницу написать недельный отчёт за пн–пт строго по регламенту.

Решения, принятые в чате 07.10:

| Вопрос | Решение |
|---|---|
| Охват | **Все проекты** пользователя, где за период были сессии или коммиты |
| Формат дня | **Карточки для таск-трекера**: Заголовок + Описание (Что сделать / Зачем / Как проверить) |
| Устройство | **Скрипт-выжимка + дневной журнал** (вариант C): неделя собирается из дневных файлов |
| Распространение | **Плагин Claude Code** в отдельном репозитории (маркетплейс с одним плагином) |
| Названия продуктов | **Общий словарь в плагине + личные дополнения** |
| claude-mem | **Необязательный** источник: без него всё работает по git и сессиям |

## Не цели

- Ничего не отправлять в таск-трекер — только готовить текст.
- Не анализировать чужую работу: только коммиты и сессии того, кто вызывает.
- Не тянуть данные с серверов (GitLab API и т. п.) — только локальные источники.

## Часть 1. Репозиторий и установка

```
work-report/
  .claude-plugin/marketplace.json        маркетплейс с одним плагином
  plugins/work-report/
    .claude-plugin/plugin.json           имя, версия, описание
    skills/work-report/
      SKILL.md                           инструкция: режимы «день» и «неделя», формат карточек
      reference/reglament.md             регламент недельного отчёта (полный текст правил)
      reference/products.json            общий словарь: имя репозитория → продукт
      scripts/digest.py                  выжимка за период (stdlib Python 3.10+)
  tests/                                 pytest на фейковых сессиях, git-репо и базе claude-mem
  docs/specs/, docs/plans/
  README.md                              установка, вызов, эталонные примеры
```

Установка у сотрудника (один раз): `/plugin marketplace add <git-url>`, затем
`/plugin install work-report`. Обновления — через обновление маркетплейса. Точный формат
`marketplace.json`/`plugin.json` и способ вызова скилла из плагина сверяются с текущей
документацией Claude Code на этапе плана.

Вызов:

- `/work-report` — карточки за сегодня; `/work-report 2026-10-06` — за указанный день;
- `/work-report week` — недельный отчёт.

Локальное состояние пользователя — `~/work-reports/` (путь меняется в конфиге):

| Файл | Содержимое |
|---|---|
| `config.json` | `authors`: список email и имён, по которым коммиты считаются своими; `reports_dir`; `extra_repos`: репозитории, где работа шла без Claude |
| `products.json` | личные дополнения к общему словарю, перекрывают его |
| `YYYY-MM-DD.md` | карточки за день |
| `week-YYYY-MM-DD.md` | недельный отчёт (дата — понедельник) |

**Свой автор.** `git config user.email` ненадёжен: у автора спека он не задан, коммиты
подписаны машинным `user@host.local`, а merge идут от аккаунта GitLab. Поэтому авторы — это
список в `config.json`. При первом запуске (файла нет) скилл предлагает кандидатов: `git config
user.email`/`user.name` и авторов коммитов, сделанных в репозиториях сессий за последние 14
дней, — пользователь подтверждает, список сохраняется.

**Продукт.** Имя репозитория — `basename` его корня (`shop_api`, `billing_api`). Название в
отчёте: сначала личный `products.json`, затем общий `reference/products.json`. Неизвестный
репозиторий выжимка помечает как `unknown`; скилл спрашивает название один раз и дописывает
его в личный `products.json`.

## Часть 2. Скрипт-выжимка `digest.py`

```
digest.py --from YYYY-MM-DD --to YYYY-MM-DD [--config PATH] [--claude-dir PATH] [--mem-db PATH]
```

Даты — включительно, по местному часовому поясу машины. Вывод — Markdown в stdout. Только
чтение, только стандартная библиотека.

### Источники

1. **Сессии Claude Code** — `~/.claude/projects/*/*.jsonl` (файлы с mtime ≥ начала периода):
   - берутся записи с `timestamp` в периоде (UTC → местное время);
   - пропускаются `isSidechain: true` (субагенты) и служебные типы;
   - репозиторий — по `cwd`: `git -C cwd rev-parse --show-toplevel`; для worktree — корень
     основного репозитория (`--git-common-dir`); если `cwd` не в git — проект без репозитория
     (имя каталога);
   - на сессию: заголовок (`ai-title`, последний), ветки (`gitBranch`), время первой и
     последней записи в периоде;
   - **сообщения пользователя** — только текст; вырезаются `<system-reminder>…`,
     `<bash-input>`/`<bash-stdout>` сокращаются до первой строки, вставки (`<pasted_content>`)
     и всё длиннее 500 символов обрезаются;
   - **ответы Claude** — последний текстовый блок каждого хода, до 800 символов; вызовы
     инструментов и их результаты не берутся.
2. **Git** — по каждому репозиторию из сессий плюс репозиториям, где есть свои коммиты за
   период (если пользователь коммитил без Claude, репозиторий берётся из `config.json` →
   `extra_repos`):
   - свои коммиты (`--author` по каждому из `authors`) из всех веток, `--no-merges`: хэш, время,
     заголовок, первые 3 строки тела, ветки, содержащие коммит;
   - merge-коммиты в `dev`/`main` за период, в чьих вторых родителях есть свои коммиты:
     время и имя ветки.
3. **claude-mem** (необязательно) — если существует `~/.claude-mem/claude-mem.db`:
   - открывается `mode=ro`; из `session_summaries` за период: `completed`, `next_steps`,
     `project`;
   - любая ошибка (нет файла, нет таблицы, другая схема, заблокирована) — источник молча
     пропускается.

### Вывод

```markdown
# Выжимка 2026-10-07 — 2026-10-07
источники: git, сессии[, claude-mem]

## Магазин (shop_api)
### Коммиты
- a1b2c3d 10-06 23:50 [fix/cart-cancel] Отмена заказа из корзины… — влито в dev 18:51
### Сессии
- 09:20–18:40 «Проверка цикла заказа» [dev]
  - пользователь: давай еще раз пройти весь цикл…
  - итог: Полный цикл заказа прошёл успешно…
### claude-mem
- сделано: …
- дальше: …

## unknown (some_repo)
…
```

Порядок продуктов — по объёму работы (число коммитов + сессий). Общий лимит — ~2000 строк;
при превышении сначала укорачиваются самые длинные сообщения, затем отбрасываются самые
старые реплики внутри сессий (заголовок и итог сессии остаются всегда).

### Маскировка секретов

До вывода маскируются: содержимое `<password>…</password>` (любой префикс), значения
заголовков/полей `X-Internal-Token`, `Authorization`, `token`, `password`, `secret`
(`key: value`, `key=value`, JSON), base64-строки длиннее 200 символов → `[base64 N байт]`.

## Часть 3. Поведение скилла (`SKILL.md`)

### Режим «день»

1. Если нет `config.json` — первичная настройка авторов (часть 1).
2. Запустить `digest.py` за день; при `unknown`-продуктах — спросить названия.
3. Сгруппировать работу в **крупные задачи**: одна карточка — один законченный результат;
   связанные коммиты и сессии одной темы объединяются; мелочи — в соседнюю карточку.
4. Карточка:
   ```
   **Заголовок:** …
   **Описание:**
   Что сделать: …
   Зачем: …
   Как проверить: …
   ```
   «Как проверить» — конкретика из истории (ручки, тесты, ID, ответы систем). Секреты,
   токены, пароли — никогда.
5. Незаконченная работа (нет merge, тест красный, ждём ответа) — пометка **«в работе»** и
   строка «осталось: …».
6. Показать карточки и сохранить в `YYYY-MM-DD.md`; если файл есть — спросить: перезаписать
   или дополнить.

### Режим «неделя»

1. Неделя — пн–пт текущей недели; в сб/вс — прошедшей (регламент: отчёт за заканчивающуюся
   неделю).
2. Взять дневные файлы за пн–пт; недостающие дни собрать выжимкой и сказать, какие дни
   добраны так.
3. Написать отчёт по `reference/reglament.md`:
   - **Что сделано за неделю** — по продуктам, результаты (не «делал/занимался»), ≤ 5 пунктов
     на продукт, строка ≤ ~160 символов, `[#…]` вместо номера задачи; незаконченное — с
     процентом готовности и тем, что осталось;
   - **Планы на следующую неделю** — из незаконченного и `next_steps` (если есть), ≤ 5 на
     продукт; продукт без планов — одна строка с причиной;
   - **Проблемы и блокеры** — только реальные, формат «что / От кого / До / Последствие»;
     неизвестные «От кого»/«До» — `___` и явная просьба заполнить;
   - пометка «РИСК СРОКА» в строке продукта — только при блокере или остановке работы.
4. Сохранить в `week-<понедельник>.md`.

## Часть 4. Регламент (`reference/reglament.md`)

Переносится полным текстом из «Регламента еженедельной отчётности» (разделы 3–5, 7):
три поля формы; группировка по продуктам; «сделано» — результат, проверка «что теперь можно,
чего нельзя было в понедельник»; планы — реальные; блокер — четыре элемента; объём ≤ 5
пунктов, ~160 символов; пример заполненного отчёта; частые ошибки. Правки регламента —
merge request в репозиторий плагина.

## Часть 5. Тесты и качество

`pytest`, данные во временных каталогах:

- **сессии:** запись в периоде и вне его; переход через полночь по местному времени;
  `isSidechain` пропущен; `system-reminder` и длинные вставки вырезаны; `cwd` worktree →
  основной репозиторий; `cwd` вне git;
- **git:** временный репозиторий с коммитами двух авторов — берутся только свои (по списку
  `authors`, включая второй email); merge в `dev` за период попадает;
- **claude-mem:** с базой; без базы; база без `session_summaries` — без падения, строка
  источников корректна;
- **маскировка:** `<password>`, `<ns:password>`, `X-Internal-Token`, `token=`, JSON
  `"password": "…"`, длинный base64;
- **словарь:** личный перекрывает общий; неизвестный → `unknown`;
- **лимит:** вывод не превышает лимит, заголовки и итоги сессий сохраняются.

Карточки и отчёт пишет модель — тестами не покрываются; в README — эталонные примеры дня и
недели, проверенные автором.

Python 3.10+ без зависимостей; `ruff` + `pytest` в CI GitLab; версия в `plugin.json` растёт с
каждым релизом.

## Открытые вопросы

- URL репозитория на GitLab (создаёт пользователь).
- Номера задач в трекере: если в именах веток или сообщениях коммитов есть шаблон номера
  (например, `SHOP-123`) — подставлять вместо `[#…]`. Шаблон компании пока неизвестен.
