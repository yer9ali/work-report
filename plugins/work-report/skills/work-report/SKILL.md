# work-report

Аргументы: `$ARGUMENTS` — пусто (сегодня), дата `YYYY-MM-DD`, `week` или `push [YYYY-MM-DD]`.

Скрипт: `python3 "${CLAUDE_PLUGIN_ROOT}/skills/work-report/scripts/digest.py"`.
Журнал: `reports_dir` из `~/work-reports/config.json` (по умолчанию `~/work-reports`).

Коды выхода скрипта: 0 — успех; 2 — неверные аргументы (дата не `YYYY-MM-DD`, `--from` позже
`--to`, неизвестная `--tz`); 3 — конфиг не JSON-объект.

Перед любым режимом запусти `digest.py --check-update`. Если он что-то напечатал — передай
это пользователю одной строкой в начале ответа и продолжай работу на текущей версии.

## 0. Конфиг (необязателен)
Свои коммиты определяются по `git config user.email` каждого репозитория — конфиг не нужен.
Если коммитов в выжимке нет, хотя пользователь коммитил (другой email на другой машине),
запусти скрипт с `--suggest-authors`, спроси, какие «Имя <email>» — его, и допиши их в
`authors` файла `~/work-reports/config.json`. Остальные необязательные поля:
`reports_dir` (по умолчанию `~/work-reports`), `extra_repos` (репозитории без сессий
Claude Code), `exclude_paths` (игнорируемые пути; `~/.claude-mem` исключён всегда).

## 1. Режим «день» (нет аргумента или дата)
1. Дата = аргумент или сегодня. Запусти `digest.py --from <дата> --to <дата>`.
2. Разбей работу на задачи: одна карточка — один результат, который можно проверить отдельно.
   Ветка и PR границу не задают: в одной ветке бывает несколько задач.
   - Решает «Зачем»: у двух карточек одно «Зачем» — склей; в одной карточке «Как проверить»
     требует двух несвязанных проверок — раздели.
   - К задаче прилипают её доделки (правки по ревью, опечатки, версия, README, тесты к ней) —
     отдельной карточкой не идут.
   - Отдельно всегда: разные продукты; баг, найденный по ходу; готовая часть и часть «в работе».
   - Мелочь без своего «Зачем» — не карточка. Несколько таких в одном продукте — одна
     карточка «[Продукт] Мелкие улучшения» со списком.
   - Проверь объём: «Что сделать» длиннее ~4 предложений или больше 3 пунктов через «;» —
     возможно, это две задачи; больше 6 карточек за день — ищи мелочи для склейки;
     одна карточка на много коммитов разных тем — ищи, что разделить. Если сомневаешься,
     сначала покажи раскладку `карточка ← коммиты/сессии` и спроси.
   Коммит с пустым смыслом («fix», «wip», «update») — посмотри `git show --stat <sha>`
   в его репозитории, прежде чем писать; не переноси бессодержательную тему как есть.
3. Карточки читают PM и заказчик без контекста кода. Заголовок — `[Продукт] ` и одно
   предложение-поручение: глагол + что («[POS] Добавить оплату картой»), даже если уже
   сделано — статус показывает трекер. Без путей, имён функций, жаргона.
   Формат — ровно такой:
   ```
   **Заголовок:** [Продукт] <Сделать что>
   **Описание:**
   **Что сделать:** <где (экран/раздел) и что, как поручение>
   **Зачем:** <какую проблему решает, кому польза>
   **Как проверить:** <что увидит человек: открыть X → нажать Y → видно Z>
   ```
   Для бага вместо «Что сделать»/«Зачем»: **Как есть сейчас:** … и **Как должно быть:** ….
   В каждой части — пара понятных предложений: где это, аббревиатуры расшифрованы при первом
   упоминании, у незнакомого продукта — одна фраза, что это. Чисто техническая правка — так и
   написать: «техническое улучшение, эффекта в интерфейсе нет»; тогда «Как проверить» — по
   тестам/ответам систем из выжимки.
4. Незаконченное (нет merge, тест красный, ждём ответа) — допиши в заголовок «(в работе)»
   и строку `Осталось: …`. Если дата — не сегодня (карточки задним числом), последней строкой:
   `Задача была выполнена <дата>, но загружена только сейчас.`
5. Покажи карточки. Сохрани в `<reports_dir>/<дата>.md` (заголовок `# <дата>`); если файл
   есть — спроси: перезаписать или дополнить. Предложи отправить их в трекер (раздел 3).

## 2. Режим «неделя» (`week`)
1. Неделя: пн–пт текущей недели; в сб, вс и пн — только что закончившейся (отчёт сдаётся
   за прошедшую неделю, даже если опоздал).
2. Прочитай `<reports_dir>/<дата>.md` за каждый день пн–пт. Для отсутствующих дней запусти
   `digest.py` за этот день и скажи, какие дни добраны так.
3. Прочитай регламент — `<reports_dir>/reglament.md`, а если его нет, `reference/reglament.md` —
   и напиши отчёт строго по нему: три поля, группировка по
   продуктам, не более 5 пунктов на продукт в «сделано» и «планах», строка ≤ ~160 символов.
   Продукт — заголовок группы из выжимки; если это имя репозитория, а в отчёте продукт
   называется иначе, спроси один раз и допиши `{"репо": "Продукт"}` в `<reports_dir>/products.json`.
   Номер задачи `[#142]` бери из дневного файла (проставлен при отправке), имени ветки или сообщения коммита (`#142`, `142-…`,
   `task-142`); если номера нет — `[#…]` и просьба пользователю вписать.
4. «Планы» — из незаконченного за неделю (и строк «дальше» claude-mem, если есть).
   «Проблемы и блокеры» — только реальные препятствия, каждый из четырёх элементов; если
   «От кого»/«До» неизвестны — `___` и явная просьба пользователю заполнить до сдачи.
5. Сохрани в `<reports_dir>/week-<понедельник>.md`.
   Недельный отчёт в трекер не отправляется (API для «Отчётов» нет) — пользователь вставляет
   его сам: «Отчёты» → «Создать отчёт».

## 3. Отправка карточек в трекер (`push [YYYY-MM-DD]` или «отправь в трекер»)
Настройки — `reference/tracker.json` (`url`, `products`: «Продукт» → `client_id`/`product_id`),
поверх него `<reports_dir>/tracker.json`, если есть. Токен — `$TASK_TRACKER_TOKEN`.
Сначала проверь: `[ -n "$TASK_TRACKER_TOKEN" ] && echo есть || echo нет` (сам токен не печатать).
«нет» — ничего не отправляй и скажи пользователю: добавить
`export TASK_TRACKER_TOKEN=mtx_pat_…` в `~/.zshrc` (или `~/.bashrc`), перезапустить Claude Code
и повторить `/work-report push`; карточки остаются в `<дата>.md`, их можно перенести вручную.
Токен в чат не вставлять — если пользователь всё же прислал его, не используй и не повторяй,
попроси отозвать и выпустить новый. Токен не записывать в файлы. Во всех запросах
`-H "Authorization: Bearer $TASK_TRACKER_TOKEN"`. Ответ `401`/`403` на первом запросе — токен
неверный или истёк: остановись и скажи выпустить новый, ничего не отправляя дальше.
1. Карточки — из `<reports_dir>/<дата>.md` (дата — аргумент или сегодня); нет файла — сначала
   режим «день».
2. Свой id: `GET <url>/users?search=<git config user.email>` → `id`.
3. Продукт карточки (`[Продукт]` из заголовка) ищи в `products`. Нет — `GET <url>/clients`,
   покажи пользователю клиентов и их продукты (только id и name), спроси, куда отнести, и
   допиши ответ в `<reports_dir>/tracker.json`. Никогда не вызывай `POST /clients` или
   `POST /products`.
4. Дубли: `GET <url>/tasks?assignee_id=<id>&search=<ключевые слова заголовка>&limit=50`.
   Похожая задача есть — покажи её `id` и `title` рядом с карточкой.
5. Покажи список «заголовок → клиент/продукт (+ возможный дубль)» и жди явного «да»/«отправляй».
   Молчание или другая тема — не согласие.
6. Каждую подтверждённую карточку — отдельным запросом, тело через quoted heredoc (кавычки и
   переносы не ломаются):
   ```bash
   curl -sS -w '\n%{http_code}\n' -X POST "<url>/tasks" -H "Authorization: Bearer $TASK_TRACKER_TOKEN" \
     -H "Content-Type: application/json" --data-binary @- <<'JSON'
   {"title": "...", "description": "...", "client_id": 14, "product_id": 11,
    "assignee_id": <id>, "status": "backlog"}
   JSON
   ```
   `title` — без префикса «**Заголовок:**», ≤255 символов; `description` — текст после
   «**Описание:**» (переносы строк в JSON — `\n`, кавычки — `\"`). Не ставить `priority`, `start_date`, `due_date`, `awards_stars` — это
   решает PM. Ответ `201` — запиши `[#<id>]` в конец заголовка карточки в `<дата>.md`
   (номер пойдёт в недельный отчёт); иначе покажи код и тело ошибки и не повторяй вслепую.
7. Итог: созданные `#id`, пропущенные, ошибки.

## Чего не делать
- **Никогда** не переносить в карточки и отчёт пароли, токены, ключи, персональные данные.
- В трекер — только через раздел 3 и только после явного подтверждения.
- Не удалять задачи и не менять чужие; статус — только `backlog` при создании.
- Не выдумывать работу, которой нет в выжимке или дневных файлах.
